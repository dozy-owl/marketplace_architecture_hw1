## О проекте
Архитектура маркетплейса

## Инструкция запуска
1. запустить Docker
2. в терминале выполнить команду `docker-compose up --build`

## Домены и их ответственность
1. Заказы: оформление заказа, трекинг статуса
2. Уведомления: отправка уведомления о смене статуса заказа
3. Поиск: поиск и персонализированная лента
4. Корзина: управление корзинами покупателей (добавить товар, удалить)
5. Каталог: хранение информации о товарах, взаимодействие продавца с товаром (добавление, удаление, редактирование)
6. Пользовательский домен: регистрация, аутентификация, авторизация, профиль
7. Платежи: расчёт и учёт платежей

## Распределение доменов по сервисам
Домен -> Сервис
1. Заказы -> Заказы (OMS)
2. Уведомления -> Уведомления
3. Поиск -> Поиск
4. Корзина -> Корзина
5. Каталог -> Каталог товаров
6. Пользовательский домен -> Пользовательский сервис
7. Платежи -> Платёжный сервис

Плюсы выделить каждому домену свой сервис:
- независимое масштабирование
- изоляция сбоев
- сильно разная реализация (по смыслу и технологическому стеку)
- разные требования к надёжности: например, для платежей очень высокая, высокая для заказов, для пользовательского сервиса можно чуть ниже и т.д.

Минусы:
- больше сетевых задержек
- модель согласованности данных усложнена
- сложнее отлаживать

Сетевые задержки важнее, когда работаем синхронно. Домены, которые обмениваются данными синхронно, добавлены в разные сервисы, только если несут слишком разную ответственность и требования к надёжности. Для остальных (домены, которые обмениваются асинхронно) можно пожертвовать сетевыми задержками в угоду перечисленным выше плюсам.

## Границы владения данными
1. Заказы: владеет БД заказов
2. Уведомления: не владеет
3. Поиск: владеет индексами поиска
4. Корзина: владеет БД корзины
5. Каталог товаров: владеет БД каталога
6. Пользовательский сервис: владеет ДБ пользователей
7. Платёжный сервис: владеет БД платежей
Сервисы отвечают за то же, за что и одноимённые домены.

Взаимодействия сервисов:
- кто с кем взаимодействует (см. диаграмму)
- каким способом (Синхронное или асинхронное) (все взаимодействия через Message Broker асинхронные, остальные – синхронные)

## Альтернативные варианты декомпозиции
1. Монолитная архитектура (единый сервис подо все домены)
2. Показанная на диаграмме архитектура
3. Архитектура, как на диаграмме, но (диаграмма*)
    - сервисы Поиск и Каталог товаров объединены в Поиск+Каталог, теперь в сервисе Поиск+Каталог 3 домена: поиск, каталог, персонализированная лента
    - сервисы Заказы (OMS) и Уведомления объединены, в сервисе Заказы+Уведомления 2 домена: заказы, уведомления

## Trade-off’ы вариантов
1. Монолит
Плюсы:
- развёртывается как единое целое
- единая база кода, проще для понимания и обслуживания
- нет зависимости от сети между сервисами для передачи информации
- простая модель согласованности данных

Минусы:
- масштабируемость всего приложения, можно нерационально использовать ресурсы
- ограниченность технологического стека/привязка к одному конкретному, нет гибкости под разные задачи
- единая точка отказа
- границы доменов размывваются

2. Архитектура с диаграммы
Плюсы:
- масштабируемость сервисов по отдельности, бережное отношение к ресурсам
- независимые сервисы, легче менять логику, сильно меньше ориентируешься на остальные сервисы
- технологический стек свой под каждый сервис
- изолированные отказы
- чёткое разделение задач сервиса

Минусы:
- каждый сервис разрабатывается и развёртывается по отдельности
- сложнее взаимодействовать между сервисами: нужны вспомогательные средства
- задержки сети при обмене данными

3. Диаграмма*
Плюсы:
- масштабируемость сервисов по отдельности, бережное отношение к ресурсам
- независимые сервисы, легче менять логику, сильно меньше ориентируешься на остальные сервисы
- технологический стек свой под каждый сервис
- изолированные отказы
- задержки сети при обмене данными меньше, чем у (2)

Минусы:
- каждый сервис разрабатывается и развёртывается по отдельности
- сложнее взаимодействовать между сервисами: нужны вспомогательные средства
- чуть более расплывчатое разделение задач между сервисами, чем у (2)

## Обоснование финального выбора
Выбор между (2) и (3) в пользу (2) обоснован выше (в объяснении выбора показанного на диаграмме разбиения на домены).

Между (2) и (1) выбран (2), т.к. описанная логика маркетплейса уже достаточно сложная, чтобы минусы монолита перевешивали плюсы: масштабируемость – что-то надо обновлять чаще (Поиск, где персонализированная лента, которую будем обновлять чаще (алгоритмы персонализации активно развиваются)), что-то реже (Корзина), технологический стек сильно разный под разные сервисы, отказ в Каталоге положит Платёж (такого быть не должно).
